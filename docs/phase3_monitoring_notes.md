# DriftShield Phase 3 — Practical Error-Change Monitoring Notes

## 1. Overview and Architecture

Phase 3 introduces online error-change detection using the River `ADWIN` algorithm on the deployed model's classification loss.

Unlike the idealized Theory Lab (which operates on a known noiseless oracle $f_0$), practical monitoring observes the stochastic 0/1 binary loss stream generated by a trained, frozen linear classifier under operational label constraints.

---

## 2. Invariant Monitoring Protocol

To preserve statistical validity and prevent observational bias, the following invariants are strictly enforced in `backend/src/driftshield/monitoring.py`:

1. **Random-Monitoring Channel Only**:
   - ADWIN receives binary losses **exclusively** from events selected via the independent random-monitoring channel (`source in ("monitor", "both")`).
   - **Selective (low-margin) labels are excluded**: Low-margin queries sample predictions near the decision boundary ($\|P - 0.5\| \approx 0$), which have an intrinsically higher baseline error rate. Mixing selective labels into ADWIN would artificially inflate the monitored error rate and trigger spurious alarms.
2. **Post-Freeze Observations Only**:
   - Model initialization and warm-up predictions are excluded. ADWIN monitoring begins only on predictions made after model freezing and scaler calibration.
3. **Loss Computation on Original Locked-In Prediction**:
   - For each legitimately delivered label at event ID `eid`, the loss is computed as:
     $$\text{loss} = \mathbb{I}[\hat{y}_{\text{orig}}(\text{eid}) \ne y_{\text{true}}(\text{eid})]$$
   - Predictions are never re-evaluated or retrospectively modified.
4. **Strict Exactly-Once Update**:
   - Each event ID can update ADWIN at most once. Duplicate deliveries are audited and rejected.
5. **Information Isolation**:
   - The detector has **zero access** to simulator hidden truth, true concept drift onset sequences, or user-injected scenario schedules.
   - Public scenario controls never trigger alerts directly.

---

## 3. Actionable Latency: Triggering Sequence vs Label Arrival

In production streams with label delays ($\text{delay} > 0$), label arrival sequence differs from the observation's original event sequence:

$$\text{arrival\_sequence} = \text{event\_sequence} + \text{label\_delay}$$

- **Triggering Observation Sequence**: The timestamp/sequence index when the model made the prediction that subsequently suffered an error.
- **Actionable Alert Sequence**: The stream sequence when the delayed label was delivered and processed by ADWIN, emitting the alert.
- **Detection Delay Metrics**:
  1. $\Delta_{\text{actionable}} = \text{arrival\_sequence} - \text{drift\_onset}$: Total elapsed stream events until an alert is actionable by operators.
  2. $\Delta_{\text{event}} = \text{event\_sequence} - \text{drift\_onset}$: Event lag of the underlying triggering observation.
  3. $\Delta_{\text{labeled}} = \text{number of post-drift monitoring labels observed}$: Physical sample cost required for statistical significance.

---

## 4. Alert Semantics & Limitations

1. **"Evidence of Error Change"**:
   - Alerts emitted by ADWIN indicate statistical evidence of a shift in the mean loss of the active model on the random monitoring channel.
   - Alerts do **not** guarantee universal drift detection, certified change boundaries, or a global false-alarm bound.
2. **Silence Does Not Imply Model Health**:
   - If the label budget is exhausted, random monitoring halts (`coverage -> 0%`).
   - If labels are delayed, ADWIN cannot update until labels arrive.
   - Lack of alarms under budget exhaustion or label starvation represents **limited observability**, not confirmed model health.
3. **Model Invariance**:
   - The active model and preprocessor remain strictly frozen during monitoring.
   - Model retraining, candidate evaluation, and promotion are reserved for subsequent phases.
